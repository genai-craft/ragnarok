# 木の探索の比較 (合成 QA、2026-10-01)

アウトライン付き PDF 5 冊 (PRML 758p、SEC Regulation Best Interest 408p、GPT-3 論文、LLaMA 2 論文、attention-residuals) の葉の節から
27B に「その節だけで答えられる質問」を 174 問作らせ (正解 = その節)、どの方法が正しい節を上位に出すかを測った。
木は PDF の埋め込みアウトライン (LLM なし) + 全ノードの 27B 要約 (50 語、インデックス時 1 回)。

| 方法 | 何をするか | hit@1 | hit@3 | hit@5 | ページ hit@1 | 呼び出し/問 | 待ち/問 |
|---|---|---|---|---|---|---|---|
| gen27b (PageIndex 方式) | 木全体を 27B に見せて節 id を生成 | 0.362 | 0.483 | 0.500 | 0.546 | 1 | 1.2 s |
| dec4b | 各階層で子を 4B 確率判定、ビーム 3 | 0.241 | 0.253 | 0.253 | 0.282 | 2.4 | 0.8 s |
| dec27b | 同上、27B | **0.460** | 0.586 | 0.598 | 0.500 | 4.0 | 4.1 s |
| emb | 節の本文の埋め込み (Qwen3-Embedding-0.6B) = 節単位のベクトル RAG | 0.534 | 0.782 | 0.851 | 0.609 | 0 | 0.01 s |
| hybrid27b | 埋め込みの部分木最大で子を 8 に絞って 27B 判定 | 0.437 | 0.575 | 0.632 | 0.477 | 4.3 | 3.6 s |
| rerank4b | 埋め込み top-10 → 4B の確率判定 1 回で並べ替え (+どれでもない) | 0.534 | 0.753 | 0.833 | 0.621 | 1 | 0.4 s |
| rerank4b+sim | 同上 + 類似度順位を 0.3 混ぜる | 0.534 | 0.833 | 0.874 | 0.621 | 1 | 0.4 s |
| **rerank27b** | 埋め込み top-10 → 27B の確率判定 1 回 | **0.569** | **0.845** | **0.897** | **0.661** | 1 | 1.4 s |

読み方:
- 木を上から辿る方式は、要約を付けて確率判定 (dec27b) にすると PageIndex 方式の生成 (gen27b) より良い (0.36 → 0.46、同じ 27B)。4B の確率判定では木を辿れない (0.24)。
- しかしこの合成 QA では **節本文の埋め込み (ベクトル) が木の探索より強い** (0.53)。質問が本文から作られているので埋め込みに有利な設定ではあるが、「ベクトル不要」をそのまま信じない方がよい、という結果。
- 一番良いのは **埋め込みで候補を取り、確率判定 1 回で並べ替える** (rerank27b 0.57 / hit@3 0.85)。4B でも hit@3 0.83 で 0.4 秒。
  これは「ベクトル RAG の rerank 段を、生成 LLM の reranker から logprob の選択に置き換える」ことに相当し、候補 10 個を 1 forward で分布として採点でき、「どれでもない」も出る。
- 木の価値はこの指標 (葉 1 つの特定) では出ていない。木が効くのは「章をまたぐ横断質問」「構造のある参照 (表・条項)」「文書に無い質問の棄却」のはずで、FinanceBench で確かめる。

## 棄却 (文書に無い質問) と 4B の蒸留 (2026-10-02)

**棄却**: 150 問を (a) 正しい 10-K、(b) 別会社の 10-K にぶつけ、rerank 最終段の「どれでもない」確率で (b) を見分けられるか。bench/fb_abstain.py。

| 判定モデル | none 確率の中央値 (正/別) | 別文書を見分ける AUROC | none > 0.5 で棄却したとき: 正しい文書の誤棄却 / 別文書の棄却 | 参考: 埋め込み最大類似度の AUROC |
|---|---|---|---|---|
| 27B | 0.03 / 0.99 | 0.985 | 0.03 / 0.90 | 0.993 |
| 4B | 0.00 / 1.00 | 0.917 | 0.01 / 0.62 | 0.998 |

「どれでもない」の確率は棄却の信号としてそのまま使える (27B: 誤棄却 3% で別文書の 90% を棄却)。ただし別会社の文書は埋め込みの類似度だけでも見分けられる (0.993) ので、この組み方では優位性は示せない。
**同一企業・別年度 (3 年以上離れた 10-K、70 問)** にぶつけると差が出る — 埋め込みは似た文書なので見分けられないが、確率判定の「どれでもない」は見分ける:

| 判定モデル | none 確率の中央値 (正/別年度) | 別年度を見分ける AUROC | none > 0.5: 誤棄却 / 棄却 | 埋め込み最大類似度の AUROC |
|---|---|---|---|---|
| **27B** | 0.02 / 0.73 | **0.960** | 0.01 / 0.79 | 0.731 |
| 4B | 0.00 / 0.00 | 0.773 | 0.03 / 0.13 | 0.731 |

→ 「その文書には答えが無い」を、埋め込みでは無理な場面 (同じ会社の別年度) で 27B の判定が誤棄却 1% で 79% 棄却する。これはベクトル RAG にも PageIndex (木を必ず降りる) にも無い性質で、jev-rag の売りの一つになる。

**4B の蒸留 (失敗)**: 評価に使わない 10-K 150 冊から 27B に 1,240 問を作らせ (出典ページが正解、埋め込み top-25 の 25 択)、openvons の凍結 4B + 学習 head (mlp、hard / 27B の soft 教師) を学習。
結果は valid 正答率 0.10 (hard) / 0.13 (soft) で、4B のゼロショット logprob 0.30、27B 0.40 に遠く及ばない。
原因: openvons の head は「選択肢の行の最終 token の hidden」を選択肢ベクトルにするので、300 文字のページ抜粋のような長い選択肢では情報が落ちる (短いラベルの判定には効くが、文章の rerank には向かない)。
問題自体も難しい (27B 教師の正答率 0.42 = 25 ページの中に同じような表が並ぶ)。4B を伸ばすなら LoRA (全体を動かす) か、選択肢ごとに 1 forward する cross-encoder 型に変える必要があり、「1 forward で 25 択」の利点とトレードオフになる。

## スキャン PDF (文字層なし): 画像埋め込み vs OCR (2026-10-08)

| 画像検索 → Qwen3-VL-8B が画像 3 枚を読んで回答 (OCR なし) | 0.50 | 0.38 |

- 英語のスキャンは **OCR なしでも画像埋め込みだけで引ける** (recall@5 0.79、Internet Archive の OCR 文字層より上)。日本語の古い活字は画像だけでは弱く、OCR が要る。
- 最良は VLM OCR (1 回きり、バッチで 1 頁 1 秒) + テキスト埋め込み (+英語は画像を 0.3 で融合) + 27B 回答。画像を VLM に直接読ませて答える経路は 8B の読解力が足りず 0.4〜0.5。
- 組み込み: `Engine(vlm_url=...)` (または `RAGNAROK_VLM_URL`) を与えると、本文の無いページを索引時に VLM で OCR する。無ければ画像埋め込みだけで検索。

### VLM を大きくしたら? (Qwen3-VL-8B → Qwen3.5-9B → Qwen3.5-27B-GPTQ-Int4、2026-10-08)

| 経路 (n=24 ずつ) | 英語 | 日本語 |
|---|---|---|
| VL-8B OCR → テキスト検索 → 27B (文字) 思考あり | **0.75** | 0.79 |
| Qwen3.5-9B OCR → 同上 | 0.54 | 0.63 |
| 画像検索 top-3 → 画像を読んで回答: VL-8B / Qwen3.5-9B / Qwen3.5-27B | 0.50 / 0.50 / 0.54 | 0.38 / 0.29 / 0.42 |
| **OCR テキスト検索 top-3 → 画像を Qwen3.5-27B が読んで回答** | 0.54 | **0.71** |
| (上限) 正解ページの画像 1 枚だけを Qwen3.5-27B に渡す | 0.88 | **1.00** |

- VLM の読解力自体は十分 (正解ページを渡せば 0.88 / 1.00)。画像経路が低かったのは **読解ではなく検索** (画像埋め込みだけの top-3) と複数ページの混同。
- 日本語は「OCR テキストで検索 → 画像を 27B VLM が読む」が最良 (0.71、OCR 誤りを回避)。英語の表は「OCR → 文字の 27B 思考あり」が最良 (0.75)。
- 質問は VL-8B の OCR から作っているので、VL-8B OCR 条件が有利に出ている点は割り引いて読む (9B OCR → 27B が低いのはその影響が大きい)。
- 結論: スキャンでも検索は OCR テキスト (+画像融合) で行い、回答は言語で切り替える (日本語: VLM に画像、英語: 文字 LLM に OCR)。

### Qwen3.8-27B (AWQ-INT4、ネイティブ多モーダル = 判定・回答に使っている同じサーバー) を読み手にした場合 (2026-10-08)

| 経路 (n=24 ずつ) | 英語 | 日本語 |
|---|---|---|
| 正解ページ 1 枚 (読解の上限): Qwen3.5-27B-GPTQ / **Qwen3.8-27B-AWQ** | 0.88 / 0.83 | 1.00 / 0.83 |
| OCR テキスト検索 top-3 → 画像を読む: 3.5-27B (1.5 倍描画) / 3.8-27B (1.1 倍描画) | 0.54 / 0.46 | 0.71 / 0.54 |
| Qwen3.8-27B で OCR → テキスト検索 recall@5 | 0.83 | 0.79 |
| Qwen3.8-27B OCR → 文字の 27B 思考あり | 0.54 | 0.67 |

- 3.8-27B (4bit AWQ) は読み手として 3.5-27B (4bit GPTQ) を上回らなかった。複数枚は描画倍率を落としたので条件が少し不利 (3 枚 × 1.5 倍だと接続が切れる → 1.1 倍)。
- 結論は変わらない: スキャンの壁は読解力より **検索** (正解ページを渡せば 0.83〜1.00)。検索は OCR テキスト (+画像融合)、回答は日本語なら画像を VLM に、英語なら OCR を文字 LLM に。
- 運用上は、**判定・回答・OCR・画像読解を 1 台の Qwen3.8-27B サーバーで賄える** (別の VL サーバーが要らない)。Qwen4-27B が出ても OpenAI 互換 + logprobs なら設定の差し替えだけ。

## 環境別の構成 (profile) — 27B が無い環境で何が残るか (2026-10-08)

FinanceBench 150 問、埋め込みは embeddinggemma-2 (+英語は画像 0.3 融合)、採点は常に 27B。判定役と回答役だけを替える。

| profile | 判定 | 回答 (思考あり) | 根拠 hit@1 / hit@5 | 回答正解率 | 必要な GPU (4bit / bf16) |
|---|---|---|---|---|---|
| **full** | Qwen3.8-27B | Qwen3.8-27B | 0.60 / **0.91** | **0.73** | 24GB 級 (AWQ 4bit ~20GB + KV) |
| **light** | Qwen3-4B | Qwen3-4B | 0.56 / **0.82** | **0.64** | 8〜12GB 級 (bf16 8GB) |
| tiny | Qwen3.5-2B | Qwen3.5-2B | 0.48 / 0.69 | 0.18 | 4GB 級 |
| nollm | なし (埋め込み順) | Qwen3.5-2B | 0.40 / 0.71 | 0.14 | 埋め込みのみなら CPU 可 (0.7 秒/頁) |

- 判定役は **4B が下限**。2B の確率判定は埋め込み順と変わらない (0.69 vs 0.71)。1.7B/0.6B のゼロショットも実験 1 で同じ結論。
- 回答役は大きさがそのまま効く: 2B 0.18 → 4B 0.64 → 27B 0.73 (金融の数値計算・判断)。検索だけ良くても回答役が小さいと落ちる。
- LLM なし (埋め込みのみ) でも根拠ページ hit@5 0.71 は出る = 「該当ページを出す」用途なら CPU だけで成立。棄却・判定・回答は無い。
- `Engine.from_profile("full"|"light"|"tiny"|"nollm")`。VRAM 実測 (vLLM): 27B AWQ 34GB (util 0.5 設定)、4B 25GB (util 0.25 設定、実体は 8GB)、2B 15GB (util 0.15 設定、実体は 4GB) — 数字は設定値で膨らんでおり、必要量は括弧内。
- openvons の「凍結小モデル + 学習 head」で 4B を 27B に近づける蒸留は失敗済 (長い選択肢に head 方式が向かない)。軽量化の現実解は light (4B) で、差は hit@5 で 9pt、正解率で 9pt。

### Qwen3.5-4B (bf16、vLLM、判定 + 回答) — light の候補として (2026-10-08)

| 4B モデル | 根拠 hit@1 / hit@5 | 回答正解率 |
|---|---|---|
| Qwen3-4B (light の既定) | 0.56 / 0.82 | 0.64 (思考) |
| **Qwen3.5-4B** | **0.52 / 0.87** | 0.49 (思考 6k、空なし) / 0.48 (思考なし) |

- 判定役としては Qwen3.5-4B の方が上 (hit@5 0.82 → 0.87、9B Q4 と同等)。回答役としては Qwen3-4B の方が上 (0.64 vs 0.49、金融の数値計算)。
- light を最良にするなら「判定 Qwen3.5-4B + 回答 Qwen3-4B」の 2 モデル構成 (bf16 で計 16GB、Q4 なら 6GB)。1 モデルなら判定重視で 3.5、回答重視で 3。

### 4B の GGUF (Q4 以下) — 4GB 級の本命 (2026-10-09)

llama.cpp (`LlamaCppBackend`)、全層 GPU、判定も回答も同じモデル。unsloth の GGUF。FinanceBench 150 問、採点は 27B。VRAM は llama-server の実測 (重み + KV cache)。

| モデル (量子化) | 重み | VRAM 8k ctx | VRAM 32k ctx ×2 | 根拠 hit@1 / hit@5 | 回答正解率 | wall (思考なし) |
|---|---|---|---|---|---|---|
| 参考: Qwen3.5-4B bf16 (vLLM) | 8GB | | | 0.52 / 0.87 | 0.49 (思考) / 0.48 (なし) | |
| 参考: Qwen3-4B bf16 (vLLM、light) | 8GB | | | 0.56 / 0.82 | 0.64 (思考) | |
| **Qwen3.5-4B Q4_K_M** | 2.7GB | | 7.9GB (128k ×8) | 0.49 / **0.85** | 0.47 (なし) / 0.37 (思考 6k) | 673s |
| **Qwen3.5-4B Q3_K_M** | 2.3GB | **3.2GB** | 4.0GB | 0.51 / **0.84** | 0.49 (なし) | 671s |
| Qwen3.5-4B UD-Q2_K_XL | 1.9GB | | 7.1GB (128k ×8) | 0.42 / 0.75 | 0.45 (なし) | 696s |
| **Qwen3-4B Q4_K_M** | 2.5GB | 4.2GB | 7.7GB | **0.57** / 0.81 | 0.50 (なし) / **0.63 (思考)** | 296s (思考 967s) |

- **判定役は Qwen3.5-4B の Q4 以下で成立する。** Q4_K_M・Q3_K_M とも hit@5 0.84〜0.85 で bf16 (0.87) からほぼ落ちず、Qwen3-4B Q4 (0.81) より上。Q2 (UD-Q2_K_XL) で初めて落ちる (0.75、埋め込み順 0.71 に近づく)。**Q3_K_M が 4GB 級の判定役の最適点** (重み 2.3GB、8k ctx で VRAM 3.2GB)。
- **回答役は Qwen3-4B Q4 の思考あり (0.63) が bf16 (0.64) と同等で、Qwen3.5-4B (0.37〜0.49) より明確に上。** Qwen3.5-4B は思考を付けると逆に落ちる (0.47 → 0.37: 6k トークンで思考が終わらない問が増える)。
- KV cache の差: Qwen3.5 (hybrid attention) は 128k ctx × 8 slot でも 7〜8GB、Qwen3 (全層 attention) は同条件で 21.5GB。長い文脈を同時に捌くなら Qwen3.5 系が軽い。
- llama.cpp 上では Qwen3.5-4B の判定が Qwen3-4B の 2.3 倍遅い (673s vs 296s、hybrid attention の実装差)。vLLM では差はない。
- 結論 (gguf profile): **判定 Qwen3.5-4B Q3_K_M + 回答 Qwen3-4B Q4_K_M** (8k ctx で計 7.4GB、重み 4.8GB) → hit@5 0.84 / 正解 0.63 = light (bf16 16GB) と同等を 4GB 級の重みで。1 モデルで 4GB に収めるなら、検索重視で Qwen3.5-4B Q3 (0.84 / 0.49)、回答重視で Qwen3-4B Q4 (0.81〜0.83 / 0.63)。
